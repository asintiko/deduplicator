## Sprint 1 «остановить кровотечение» — выполнено

Реализованы P0-пункты из раздела 9 аудита (приоритетный порядок):

1. **Троттлинг прогресса** — `src/Deduplicator.Core/Engine/ProgressCoalescer.cs`.
   Per-file `Report` больше не дёргает UI на каждый файл: события сглаживаются (~8/сек),
   смена этапа/завершение/ошибка отдаются немедленно. Подключён в `ScanService`.
2. **План чтения на каждый том** — `src/Deduplicator.Core/Engine/VolumeReadPlan.cs`.
   Удалён глобальный `_parallelism`, который при наличии одного HDD делал весь скан
   однопоточным. Теперь HDD/съёмные читаются последовательно, SSD/NVMe — параллельно;
   один HDD больше не «душит» SSD. `ComputeParallel` группирует файлы по тому и читает
   каждый том со своим DOP, тома — параллельно. План пишется в лог.
3. **Проверка стабильности размера** — `HashService.ComputePartialHash/ComputeFullHash`
   сверяют длину файла до и после чтения; при изменении бросают
   `FileChangedDuringScanException`. `ScanService` ловит её и пропускает файл (хэш не
   сохраняется, счётчик `FilesChangedSkipped`).
4. **Безопасность побайтовой сверки** — `DuplicateGrouper.ByteVerifyClusters`.
   Если оба файла подключены, а сверка байтов бросает исключение, файл **не** считается
   дублем (раньше — `equal = true`, доверие хэшу). Отключённый носитель по-прежнему
   даёт hash-only группу (которую нельзя автоудалять).
5. **AutoSelect только для точных** — `ResultsViewModel.AutoSelectAll` доступен лишь на
   вкладке точных дубликатов; похожие фото/музыка отмечаются исключительно вручную.
6. **Составные индексы SQLite** (раздел 5.2) добавлены в `Schema.cs`
   (`idx_files_size_id`, `idx_files_size_partial`, `idx_files_size_full`,
   `idx_files_volume_size`, `idx_files_category_state`) — идемпотентно для существующих БД.

Новые тесты: `tests/Deduplicator.Core.Tests/Sprint1EngineTests.cs`
(стабильность размера, безопасность сверки, план чтения на том, троттлинг прогресса).

## Состязательное ревью Sprint 1 — результаты

Запущено многоагентное ревью (5 измерений → проверка каждой находки на опровержение):
**9 подтверждено, 6 опровергнуто**. Исправлено по итогам:

- **Нечитаемая «голова» кластера** (HIGH): сверка шла только с `c[0]`, и нечитаемый файл-голова
  ложно разрывал настоящую пару дубликатов. → `ByteVerifyClusters` переписан: якорем может быть
  только подключённый и реально читаемый файл (проба `IsReadable`).
- **Офлайн-«голова» коротко замыкала сверку** (HIGH, потеря данных): офлайн-голова делала
  `equal=true`, из-за чего два РАЗНЫХ подключённых файла могли слиться в группу 1.0 при коллизии
  хэша. → подключённые файлы кластеризуются строгой попарной сверкой друг с другом; офлайн —
  только hash-only члены.
- **Hash-only группы без маркера** (HIGH): теперь такие группы получают `Confidence < 1.0`, а
  `AutoSelectAll` их пропускает (плюс прежний бэкстоп — нельзя удалить файл с `FullPath==null`).
- **Переподписка потоков** (HIGH): вложенный `Parallel.ForEach` мог разрастаться по числу томов.
  → общий потолок одновременных чтений через `SemaphoreSlim` в `ComputeParallel`.
- **Поздний stale-эвент прогресса** (MEDIUM): trailing-таймер мог выстрелить после терминала.
  → `ProgressCoalescer` снимает таймер на immediate/Flush и джойнит callback в `Dispose`.
- **Мигание этапа «Полный хэш»** (LOW): этап переключался даже без работы. → `SetStageQuiet`
  вызывается только когда `needFull.Count > 0`.

Отложено (не Sprint 1):
- Параллельное перечисление по томам в `Enumerate` (сейчас тома обходятся последовательно) — войдёт
  в Sprint 3 (стратегия перечисления).
- Несогласованный знаменатель прогресса в `HashFunnel` (косметика %, предсуществующая) — Sprint 2.
- Проверка стабильности только по длине, не по содержимому (grow→truncate в то же значение):
  низкий риск, бэкстопом служит обязательная побайтовая сверка перед удалением.
- Полноценный флаг hash-only в модели/БД и запрет автоудаления на уровне модели — Sprint 2.

## Sprint 2 «настоящая интеграция движка» — выполнено

Главный тезис аудита («`ScanService` — это старая SQLite/hash-воронка с быстрым lister сверху»)
закрыт: exact-путь переведён на потоковый движок.

- **Контракт** `IExactDuplicateEngine` + `ExactScanRequest`/`ExactScanResult`/`IExactScanReporter`
  (`src/Deduplicator.Core/Engine/IExactDuplicateEngine.cs`).
- **`ExactDuplicateEngineV2`** — потоковая воронка: size-кандидаты одним запросом → частичный хэш →
  полный хэш только для коллизий → точные группы с безопасной побайтовой сверкой. Per-volume DOP,
  stable-size, hardlink-aware группировка (через прежний безопасный `DuplicateGrouper`).
- **N+1 убран**: `FileRepository.StreamDuplicateSizeCandidates()` — один `ORDER BY size`-запрос
  вместо `GetDuplicateSizeCandidates()` + цикла `GetBySize()`. На 1M файлов с уникальными размерами
  кандидатов 0 → содержимое не читается вовсе (проверено тестом `Sprint2EngineTests`).
- **Concurrency-фикс (2 итерации)**: (1) потоковый reader на shared-cache блокировал запись хэшей →
  busy_timeout 30с (поймано тестом-зависанием). (2) ревью доказало эмпирически, что долгоживущий
  read-mark не даёт чекпоинту освобождать WAL → рост WAL на гигабайты. Итоговое решение: кандидаты
  читаются ПАЧКАМИ размеров (`GetDuplicateSizeCandidates` + `GetBySizesOrdered` по 200) —
  короткоживущий reader закрывается до записи, между пачками `PassiveCheckpoint`. Не N+1 и WAL не растёт.
- **`ScanService` стал фасадом**: `RunCore` зовёт `_exactEngine.ScanExact(...)`; `HashFunnel`
  удалён; точная группировка переехала в движок; адаптер `ScanReporter` прокидывает прогресс/паузу/
  сессии; `ComputeParallel` и движок используют общий `VolumeParallelExecutor`.
- Тесты: `Sprint2EngineTests.cs` (уникальные размеры не читаются; streaming-выборка без N+1;
  бюджет параллелизма по томам). Паритет со старой воронкой подтверждён тем, что все прежние тесты
  (вкл. EndToEnd на реальном корпусе через настоящий `ScanService`) зелёные.

Состязательное ревью Sprint 2 (4 измерения): **SQLite-конкурентность и паритет — опровергнуты**.
Подтверждено: (HIGH) рост WAL из-за долгоживущего read-mark → исправлено пачками размеров (выше);
(medium) потолок чтений брал МАКСИМУМ DOP вместо СУММЫ → `VolumeParallelExecutor.GlobalCap` (сумма ≤
2× ядер); (low) двойной ярлык «Группировка» и мигание «Анализ похожих» без работы → этап выставляется
только при наличии работы; (low) неиспользуемый параметр убран.

## Sprint 3 «MFT/USN правильно» — выполнено (логика покрыта тестами)

- **`BackendSelector`** (чистая функция, тесты; заменил `EnumeratorSelector`): MFT — только для ЦЕЛОГО
  тома NTFS под админом; вложенная папка / exFAT / без админа / не-Windows / сеть → совместимый

## Финальный MVP «быстрый скан на всех дисках» — выполнено (P0), P1-гард частично

Матрица бэкендов (раздел «Backend decision matrix» ТЗ) реализована и протестирована:

| Цель | ФС | Админ | Скоуп | Бэкенд | Сообщение |
|---|---|---|---|---|---|
| том | NTFS | да | весь том | `NtfsMft` | турбо NTFS/MFT включён |
| том | NTFS | нет | любой | `Win32Find` | совместимый режим; **для MFT** можно от админа |
| том | exFAT/FAT32/ReFS | любой | любой | `Win32Find` | exFAT — совместимый режим (**без упоминания админа**) |
| папка | NTFS | да | подпапка | `Win32Find` | быстрый обход выбранной папки |
| UNC/сеть | — | любой | любой | `Win32FindNetwork` | сетевой режим, скорость зависит от сети |

- **ГЛАВНОЕ исправление UX:** для НЕ-NTFS дисков сообщение больше НИКОГДА не предлагает «запустите от
  администратора» (это не создаёт MFT на exFAT/FAT32). Покрыто тестом `NonNtfs_Admin_DoesNotSuggestAdmin`.
- **`Win32FindMetadataEnumerator`** (`FindFirstFileExW` + `FindExInfoBasic` + `FIND_FIRST_EX_LARGE_FETCH`):
  размер/время/атрибуты приходят прямо из `WIN32_FIND_DATA` — **убран второй `stat` на каждый файл** в
  fallback-пути (было главным тормозом на exFAT/USB/сети для 100k–1M файлов). Ручной стек (без рекурсии),
  reparse/hidden/excluded-фильтры, длинные пути и UNC. Тест: полнота = `Directory.EnumerateFiles` + метаданные.
- MFT-путь сохранён (`USN` → stat), т.к. USN-записи не содержат размер/время.
- **Диагностика:** лог переехал в `%LOCALAPPDATA%\Deduplicator\logs\deduplicator.log` (стартовый баннер
  версии/прав/путей + строка `Backend ... FileSystem=... Backend=... Reason=... IsAdmin=...` на каждый корень).
- **Память результатов (P1):** вкладки «Похожие» строятся ЛЕНИВО (миниатюры декодируются только при
  открытии вкладки); точная вкладка показывает ПЕРВУЮ страницу (100 групп) + кнопка «Показать ещё»
  (`ShowMoreExactCommand`/`CanShowMoreExact`). Авто-выбор и экспорт достраивают все группы
  (`EnsureAllExactBuilt`/`EnsureImageBuilt`/`EnsureAudioBuilt`), оставаясь полными; путь удаления не тронут.
  Остаётся (не для MVP): полная виртуализация списка.

## Второй аудит projact(2) — правки P0

- **Scope-aware группировка** (главное): `BuildExactGroups`/`BuildSimilarImage`/`BuildSimilarAudio`
  принимают `inScope` и строят группы ТОЛЬКО из файлов текущей области. Раньше группировка шла по
  всей базе (`GetSharedFullHashes`/`GetByFullHash` глобально) — после скана папки B могли показаться
  дубликаты из старого индекса папки A, и пользователь мог удалить непросканированное. Тест: скан A
  (дубли) → скан B (без дублей) → группы A не показываются.
- **Hardlink-aware reclaimable**: `DuplicateGrouper.CollapseHardlinks` (через публичный
  `FastDedup.Engine.FileIdentityReader` = `GetFileInformationByHandle`) схлопывает алиасы по
  VolumeSerial+FileIndex; `ReclaimableBytes` — по уникальным физическим файлам; группа только из
  hardlink-ов не показывается как удаляемая. Тест на NTFS.
- **Строгий fingerprint переиспользования хэшей**: убран допуск `±2с` по mtime — теперь точное
  совпадение size+mtime+created (добавлено в `ExistingFileMeta`). Файл, переписанный содержимым того
  же размера, больше не получает старый хэш по «близкому» времени.
- **USN без потерь**: `UsnEnumerator` откатывается на обычный обход при ЛЮБОЙ записи неподдерживаемой
  версии (раньше — только при >20%), чтобы не пропустить файлы молча.
- **Long-path**: `ByteVerifyClusters` использует `LongPath.Fix` в `File.Exists`.
- **Packaging/диагностика**: `scripts/publish-win-x64.ps1` (чистый publish + проверка, что
  `FastDedup.Engine.dll` и новые символы реально в output) — закрывает риск «старый dist». Проверено:
  publish self-contained СОДЕРЖИТ `FastDedup.Engine.dll`, `deps.json` его упоминает, `Core.dll`
  содержит `ExactDuplicateEngineV2`. `EngineBuildInfo` логирует версии при старте скана.

**88 тестов зелёные**, Release 0/0.

## Третий аудит projact(3) — правки безопасности

- **P0.1 session-scoped группы**: `duplicate_groups.scan_session_id` (+миграция, индекс); `InsertGroups`
  помечает группы сессией; `ClearGroupsNotInSession(sessionId)` вызывается ПОСЛЕ успешного скана и
  убирает группы прошлых запусков. Теперь после `ExactOnly`-скана НЕ показываются «похожие» из
  прошлого скана (нельзя отметить/удалить файлы вне текущего запуска). Тест.
- **P0.2 hash-only/офлайн точные группы не удаляемы**: `FileItemViewModel.CanMark =
  GroupAllowsDeletion && !IsProtected && FullPath!=null`. Для точных групп с `Confidence<1.0`
  (есть непрочитанные/офлайн члены) чекбоксы и кнопки удаления отключены; в карточке — предупреждение
  «проверьте ещё раз». Авто-отметка уже исключала их.
- **P0.3 «похожие» не показывают точную экономию**: `ReclaimableBytes=0` для similar в БД + UI пишет
  «Похожие — проверьте вручную» вместо «Можно освободить X».
- **P1.5 пропуск скрытых/системных папок**: `FallbackEnumerator` не заходит внутрь hidden/system
  каталогов (`AttributesToSkip |= Hidden|System`) при `SkipHiddenSystem`. Тест.
- **P2.3 диалог удаления** перечисляет, сколько будет перемещено в Корзину и сколько заблокировано/
  недоступно (не будет тронуто).
- **P3.2 гигиена**: отчёты с кириллицей перенесены из корня в `docs/reports/`; `dist/` в `.gitignore`.

## Sprint 19 «USN-дельта-реконсайл» (3.1 аудита 2026-07-02) — выполнено (2026-07-03)

Закрыт пункт «Не сделано» Sprint 4: том с НЕБОЛЬШИМИ изменениями больше не пересобирается целиком —
читается только дельта журнала и переиндексируются ТОЛЬКО изменённые файлы (1M файлов + сотня
изменений: минуты обхода → секунды).

- **`UsnDeltaReader`** (`src/FastDedup.Engine/Enumeration/UsnDeltaReader.cs`) — FSCTL_READ_USN_JOURNAL
  (READ_USN_JOURNAL_DATA_V0) от сохранённого водяного знака до NextUsn снимка на старте скана;
  восстановление путей по FRN родителей (OpenFileById + GetFinalPathNameByHandleW в `Native`),
  карта всей MFT НЕ строится. Разбор записей — общий с MFT-перечислением (`UsnRecordParser`,
  вынесен из `UsnEnumerator`). Typed-результат: список изменений ЛИБО «дельта недоступна, причина»
  (усечение журнала 1181/1178/1179, версия записи ≠ V2, запись без имени, кап 100 000 записей,
  невосстановимый путь) — никаких исключений наружу.
- **`UsnDeltaPlanner`** (Core, чистый) — классификация Reason-масок: файловые FILE_DELETE/RENAME_OLD →
  удалить строку по пути; остальное → пере-stat (диск — источник истины, порядок записей не важен);
  каталожные rename/delete → аномалия (полный пересбор тома — вложенные пути точечно не реконсайлятся).
  Группировка по Ordinal-пути (смена регистра = Delete(старый)+Restat(новый)).
- **`UsnDeltaExecutor`** (Core) — применение плана через хуки (stat/index/delete/volume-alive):
  валидация всех путей ДО изменений БД; restat-промах при живом томе → строка удаляется, при мёртвом →
  аномалия (носитель выдернули ≠ «файлы удалены»); отфильтрованный после изменения файл (скрытый,
  $Recycle.Bin, категория) → строка удаляется (в полном скане её убрал бы прунинг; держать старый хэш
  изменённого содержимого опасно). Любой сбой посреди применения → аномалия → полный пересбор.
- **`ScanService`**: обработка одного файла вынесена в `VolumeIndexer` (общий код перечисления и
  дельты — фильтры/категории/строгое переиспользование 2.7 не могут разойтись); изменённые файлы идут
  через обычный `UpsertMetaBatch` → хэши и verified_full_hash сбрасываются сами. При успешной дельте
  том ведёт себя как Unchanged: prune/seen НЕ выполняются, в scan_scope_files не пишет (сознательно
  идентично skipVolumes). Watermark: тот же snap.NextUsn начала скана — дельта применена ровно до
  него, хвост дочитает следующий скан (идемпотентно). `FileRepository.DeleteByVolumeAndPath` — новое.
- Диагностика: «Быстрое обновление по журналу USN (X:): изменений N, удалений M» на карточке скана;
  причина любого отката на полный пересбор — в логе.
