# Аудит и план развития Deduplicator — 2026-07-02

Три части: **(1)** аудит багов, **(2)** план доведения интерфейса до профессионального уровня, **(3)** дорожная карта ускорения движка (внешние носители + слабые ПК).

Методика: 7 охотников за багами по измерениям (внешние носители, отмена/конкурентность, безопасность данных, память, состояние VM, целостность БД, крайние входы), каждая находка — адверсариальная проверка двумя независимыми скептиками по реальному коду; 4 UX-аудитора + синтез; 5 архитекторов идей + технический судья. Часть верификации завершена вручную по коду.

## Часть 2. План интерфейса до профессионального уровня

(Синтез из 48 предложений 4 аудиторов; 35 уникальных.)

### Сквозные темы

1. **Обратимость и контроль** — undo спрятан, отметки нельзя снять, объём выбранного не виден.
2. **Честность текстов** — UI говорит «Корзина», когда работает карантин; советы, которые невозможно выполнить.
3. **Инструменты решения** — приложение требует «проверьте похожие вручную», но не даёт ни просмотра, ни сравнения, ни метаданных.
4. **Визуальная система** — цвета кнопок, тёмная тема, диалоги — копипаста с расхождениями.
5. **Клавиатура и доступность** — ноль KeyBinding, ноль AutomationProperties.
6. **Навигация** — половина реализованных экранов недостижима.

### MUST — топ-10

| # | Что | Суть |
|---|-----|------|

1. Правила авто-выбора (оставить эталон / новейший / старейший / предпочитать папку) + «Сделать эталоном» + предпросмотр.

### Этап 2. Ядро v2.1 (недели) — приоритет: фото с внешних носителей + слабые ПК

- **2.1 Батчинг хэширования + LCN-сортировка** (один HashByVolume на пачку из 200 размеров; сортировка чтений по первому LCN через `FSCTL_GET_RETRIEVAL_POINTERS`, без админа) — **самая важная работа**: 2–5× партиал-этап на внешнем HDD. Нужны тесты эквивалентности групп.
- **2.2 Пакет Imaging** (TargetSize=128–256 декод c scaled-IDCT, 8 ориентаций на ужатой копии, потоковый pixel-hash без `new byte[W*H*4]`, Identify-префильтр, кап аллокатора 64 МБ): декод 24 МП JPEG 5–10× быстрее, RAM-пики режутся кратно. **Обязательно `phash_ver` + bump EngineVersion** (pHash смещается на единицы бит).
- **2.3 Пропагация pHash по full_hash** — байт-идентичные копии не декодировать: ~2× перцептив на библиотеках с 50% копий.
- **2.4 Конвейер чтение→декод** (продюсеры по плану тома, bounded Channel ~128 МБ, декодеры = ProcessorCount): потолок = линейная скорость диска, а не «диск ждёт одно ядро».
- **2.5 Кэш verified_full_hash** — повторный скан той же флешки без чтения содержимого: минуты → секунды (RevalidateBeforeDelete не трогаем).
- **2.6 Губернатор ресурсов** (EWMA-throughput на том: probe DOP +1/откат; USB2 → 1; сжатие пачек при нехватке RAM): слабые ПК перестают уходить в своп.
- **2.7 Стриминг метаданных при Incremental** (IN-lookup чанками по 400 вместо словаря всего тома): −250–400 МБ на 1М-файловом томе. Проверить, что словарь не нужен для обнаружения удалённых.
- **2.8 Прогрессивные результаты** (exact-таб доступен после Grouping; удаление заблокировано до конца сессии): первые результаты через минуты вместо часа.
- **2.9 Режим «Эко»** (BelowNormal + IO_PRIORITY_HINT=Low + EcoQoS; ContentDop=1): скан не душит 2-ядерный ноутбук. PROCESS_MODE_BACKGROUND целиком не использовать.
- **2.10 Умные правила хранения** (KeepScorer: Downloads/Temp, «копия»/«(1)», разрешение/EXIF; бейдж-причина; только предвыбор) — главный продуктовый дифференциатор этапа.
- **2.11 Меньшее:** RAM-aware выбор MFT-бэкенда; параллельный Win32Find (UNC/exFAT в разы); профили устройств (\DCIM → фото-режим); FSCTL_QUERY_FILE_LAYOUT — после остальных.

### Сквозные правила

1. **Безопасность данных не деградирует ни одной идеей** — все ускорения до порога byte-verify и RevalidateBeforeDelete, которые не трогаем.
2. **Версионирование обязательно:** 2.2 → `phash_ver`; 1.6 → `partial_ver`; 2.5 → строгий признак переиспользования метаданных.
3. **Каждая перф-работа — с числами:** телеметрия (1.1) до всего; «до/после» на трёх эталонных носителях (USB2-флешка, USB3-SSD, внешний HDD).
4. **Критический путь этапа 2:** 2.1 → 2.2 → 2.4 → 2.8.
