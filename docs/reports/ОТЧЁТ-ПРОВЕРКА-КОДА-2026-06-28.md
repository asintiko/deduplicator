## 1. Общий вердикт

**Архитектура зрелая и здравая.** Сверка идёт по содержимому (а не по имени/атрибутам),
семиступенчатая воронка хэширования с финальной побайтовой сверкой, атомарная запись
(временный файл → flush → переименование), межтомовый перенос с проверкой по хэшу,
SQLite в режиме WAL с транзакциями. Для типовой библиотеки (≤ 1 млн файлов) работает
корректно и в разумной памяти.

**До передачи клиенту стоит закрыть несколько локальных дефектов** (правки на 1–2 дня,
не переписывание): крах при старте, если БД/папка недоступны; «тихие» пропуски дубликатов
на очень больших наборах; утечки COM-объектов WMI; шероховатости пакетных файловых операций.
Критических потерь данных не обнаружено.

## 2. Ответы на вопросы клиента

### 2.1. Сколько памяти съест «кэш»?

Нужно разделять три разные вещи:

**(а) Кэш SQLite в оперативной памяти — практически ничтожен.**
`PRAGMA cache_size` не задан → дефолт ~2 МБ на соединение; соединения короткоживущие,
пул общий. WAL добавляет ещё десятки МБ. Итого единицы–десятки МБ. Не проблема.

**(б) Постоянная БД на диске («слепки» файлов) — это и есть растущий «кэш».**
Одна запись о файле ≈ **0,4–0,7 КБ** (путь + даты + хэши + 5 индексов). Для аудио больше
из-за отпечатка Chromaprint (~0,5–2 КБ/трек). Ориентир:

| Файлов | БД на диске |
|---|---|
| 100 тыс. | ~50 МБ |
| 1 млн | ~0,5 ГБ |
| 10 млн | ~5 ГБ (+ аудио) |

**(в) Рабочая память во время сканирования/группировки — главный потребитель RAM.**
Перечисление файлов и хэширование идут потоково (батчи по 2000) — это хорошо, память мала.
**Но этап группировки «похожих» грузит весь набор категории в RAM целиком:**

- [DuplicateGrouper.cs:131](src/Deduplicator.Core/Matching/DuplicateGrouper.cs:131) — `GetByCategoryWithPerceptual(Image)` загружает **все** изображения в один `List<FileRecord>` + параллельный словарь `byId` (те же объекты ещё раз) + словари `hashOf`/`buckets`/`lshRows` (LSH-строк в ~8 раз больше числа картинок).
- [DuplicateGrouper.cs:210](src/Deduplicator.Core/Matching/DuplicateGrouper.cs:210) — то же для аудио.
- [ScanService.cs:266-280](src/Deduplicator.Core/Services/ScanService.cs:266) — на каждый размер `GetBySize()` материализует все файлы этого размера (пик на «вырожденной» группе одинакового размера).

Оценка пика RAM:

| Сценарий | Пик RAM при сканировании |
|---|---|
| Только точные дубликаты (любой объём) | десятки–сотни МБ (потоково) |
| «Похожие фото», 100 тыс. изображений | ~150–250 МБ |
| «Похожие фото», 1 млн изображений | ~0,5–0,7 ГБ |
| «Похожие фото», 5–10 млн изображений | **2–4 ГБ и выше → риск OOM** на 8 ГБ ОЗУ |

**Вывод для клиента (миллионы фото на разных дисках):** режим *точных* дубликатов
масштабируется без проблем. Режим *похожих* фото держит весь список в памяти, и на
многомиллионных библиотеках память растёт линейно вплоть до нехватки.
**Рекомендация:** стримить/постранично обрабатывать `GetByCategoryWithPerceptual` и
`GetBySize` вместо `.ToList()`, не держать одновременно и список, и словарь `byId`,
по желанию вынести `PRAGMA cache_size` в настройки. Для текущего масштаба клиента —
допустимо, но потолок надо задокументировать.

### 2.2. Сверка глубже атрибутов? Узнает ли переименованный файл? Разные диски, разные имена?

**Да. Это самая сильная часть программы.**

- **Сверка по содержимому, не по имени.** XxHash128: частичный (64 КБ с краёв + размер) →
  полный → финальная **побайтовая** сверка ([HashService.cs](src/Deduplicator.Core/Hashing/HashService.cs)).
  Переименование **не приводит к промаху** — имя в сверке не участвует.
- **Нюанс по переименованию (производительность, не корректность).** Кэш переиспользования
  хэшей привязан к `(том, относительный путь, размер, mtime)`
  ([ScanService.cs:200-206](src/Deduplicator.Core/Services/ScanService.cs:200)). При
  переименовании путь меняется → файл **пере-хэшируется заново** (лишняя работа), но дубликат
  всё равно найдётся. На HDD массовое переименование (десятки тысяч файлов) удлинит следующее
  сканирование. Это ровно тот «длительный процесс», о котором писал клиент — да, мгновенным
  он не будет, и это нормально.
- **Разные диски, разные имена.** Поддержано: `GetCrossVolumeDuplicates()`
  ([FileRepository.cs:100-121](src/Deduplicator.Core/Data/FileRepository.cs:100)) находит
  одинаковое содержимое на 2+ томах. Совпадения сохраняются, **даже если диск потом отключить**,
  при условии что оба диска были просканированы хотя бы раз.
- **Похожие фото (сжатые/уменьшенные/повёрнутые/переименованные).** Перцептивный pHash
  ([ImageMatchService.cs](src/Deduplicator.Core/Imaging/ImageMatchService.cs)) + опционально
  инвариантность к поворотам + pixel-hash для одинаковых картинок в разных форматах (JPG/PNG).
  Аудио — отпечаток Chromaprint + MinHash/LSH.

См. также проблему **H2** ниже — на очень больших наборах часть похожих может «теряться».

### 2.3. Защита от потери данных при сбое записи/перезаписи или пропадании питания?

**Да, в целом защита есть.** Основные механизмы крепкие; есть несколько узких окон,
касающихся *записей для отмены*, а не самих файлов.

Сильные стороны:
- Атомарная запись: временный файл с `FileOptions.WriteThrough` + явный flush на диск +
  атомарное переименование ([SafeIo.cs:20-44](src/Deduplicator.Core/Util/SafeIo.cs:20)).
  При сбое остаётся либо старый файл, либо ничего — но не «половина».
- Межтомовый перенос: хэш источника → копия → хэш приёмника → **источник удаляется только
  при совпадении хэшей** ([SafeIo.cs:51-73](src/Deduplicator.Core/Util/SafeIo.cs:51)).
  Даже «тихое» повреждение не приведёт к потере.
- Удаление — только в Корзину Windows или карантин (обратимо), с журналом операций.
- Очистка осиротевших временных файлов при старте
  ([Composition.cs:25](src/Deduplicator.App/Composition.cs:25)).
- БД: WAL, `synchronous=NORMAL`, внешние ключи, busy_timeout 30 с, запись в транзакциях.

Узкие места (детали в §3):
- Запись в журнал операций делается **после** физического перемещения файла
  ([FileOpsService.cs:55-112](src/Deduplicator.Core/Services/FileOpsService.cs:55)). Сбой
  питания в этом окне → файл безопасно лежит в карантине/корзине, но **запись для «Отмены»
  потеряна** (восстановить можно вручную из папки карантина / Корзины Windows). Это потеря
  *записи отмены*, не файла.
- Временная жёсткая ссылка `.dedup-hl` может осиротеть и не вычищается при старте
  (чистится только `.dedup-tmp`).
- Перенос дерева каталогов не делает поэлементную пере-сверку по хэшу (в отличие от
  одиночного файла) — риск низкий за счёт `WriteThrough`+атомарного переименования.

### 2.4. Много работы с копированием/перемещением/переименованием/удалением (раскладка по папкам и дискам)

**Одиночные операции безопасны** (атомарны, с проверкой). **Для крупных миграций пока не
«промышленный» уровень** — это не баги-падения, а отсутствующие удобства и страховки:

- Прогресс по **числу файлов**, а не по байтам → оценка времени бессмысленна на разнородных размерах.
- **Нет повторных попыток** при временной блокировке файла / моргании USB → элемент просто падает в ошибку.
- **Нет паузы/возобновления и точки рестарта** для пакета; повторный запуск в непустую папку даёт коллизии.
- **Нет журнала отмены для перемещения/копирования** (обратимо только удаление).
- Частичный сбой пакета: текущий элемент логируется в ошибки, остальные продолжаются — это правильно,
  но без отката уже сделанного.

Рекомендация: прогресс по байтам; повтор с back-off на временных ошибках; проверка полноты
копии дерева перед удалением источника; резюмируемый план по элементам; различать тип ошибки
(занят / нет места / нет прав) в интерфейсе.

## 3. Подтверждённые проблемы (по серьёзности)

### Высокая

**H1. Крах при старте, если БД/папка недоступны.**
[Composition.cs:19-22](src/Deduplicator.App/Composition.cs:19) — `new AppPaths()` и
`database.Initialize()` без try/catch; вызывается из `async void` без обёртки. Повреждённая
БД / нет прав на запись / диск полон → необработанное исключение, приложение падает на старте
без понятного сообщения.
*Чинить:* обернуть инициализацию в try/catch, показать пользователю ошибку/восстановление.

**H2. На больших наборах часть похожих дубликатов «теряется» молча.**
[DuplicateGrouper.cs:181](src/Deduplicator.Core/Matching/DuplicateGrouper.cs:181) (и аудио
[:255](src/Deduplicator.Core/Matching/DuplicateGrouper.cs:255)). При >5000 изображений
переход на LSH; если одна корзина LSH содержит >1500 элементов (`BucketPairCap`), она
**целиком пропускается** (`continue`) без сравнения и без предупреждения. На многомиллионных
библиотеках с плотными корзинами часть истинных совпадений не находится. Для поисковика
дубликатов тихие пропуски — чувствительный дефект (актуально именно для сценария клиента).
*Чинить:* дробить большие корзины (под-band/чанки) вместо пропуска; как минимум — логировать,
что сравнение было ограничено.

**H3. Аудио-ветка не дедуплицирует список перед проверкой лимита корзины.**
[DuplicateGrouper.cs:255](src/Deduplicator.Core/Matching/DuplicateGrouper.cs:255) — проверяет
`list.Count` по «сырому» списку и итерирует его же, тогда как ветка изображений сначала
`DistinctByHash` ([:180](src/Deduplicator.Core/Matching/DuplicateGrouper.cs:180)). Несогласованность
→ лишние пропуски/повторные сравнения.
*Чинить:* применить `DistinctByHash` и в аудио-ветке.

**H4. Утечка COM-объектов WMI в VolumeService.**
[VolumeService.cs:83-93](src/Deduplicator.Core/Services/VolumeService.cs:83) — оба цикла по
`searcher.Get()` не освобождают `ManagementBaseObject` (каждый — COM-обёртка). Путь горячий
(инициализация + реакция на подключение/отключение дисков) → накопление хэндлов.
*Чинить:* обернуть каждый объект в `using`.
